BINARY MARKET INTELLIGENCE
FULL PROJECT ARCHITECTURE AND CODE EXPLANATION
============================================================

Document purpose
----------------
This document explains the repository as a complete system: structure, runtime
processes, data flow, modules, agents, the effective master-agent behavior,
providers, storage, APIs, frontends, browser observation, tests, deployment,
and known gaps. It is based on a source-level review of the project files.

The project contains two related but mostly separate runtime families:

1. Primary TypeScript market-intelligence platform
   - HTTP API and dashboard
   - logical analytical-agent registry
   - market-data providers and live pipelines
   - validation, probability, risk, and simulation engines
   - PostgreSQL persistence
   - Redis job infrastructure

2. Secondary Python/local relay and browser-observation system
   - local WebSocket relay
   - Deriv/Finnhub forwarders
   - SQLite persistence
   - standalone frontend dashboard
   - browser extension and screen-observation tools

The two families share the repository but do not share one complete persistence
or deployment path. The TypeScript service is the main documented backend.

IMPORTANT PRODUCT BOUNDARY
---------------------------
This is an analytical and simulation system. It is not a live-trading bot.
Signals are marked ANALYTICAL_SIGNAL and executionOrder is false. Binary-option
providers are blocked, unverified, or unsupported unless a permitted data
interface is explicitly verified. The system is intentionally fail-closed and
can return NO_SIGNAL instead of inventing a decision.

============================================================
1. EXECUTIVE SYSTEM VIEW
============================================================

High-level request pipeline
---------------------------

HTTP POST /api/v1/analysis
  -> parse and validate request JSON
  -> build AnalysisRequest
  -> select relevant ACTIVE/DEGRADED agents
  -> execute selected agents through bounded worker pool
  -> apply per-agent timeout and retry policy
  -> isolate failed agents
  -> aggregate evidence and probabilities
  -> calculate agreement and data-quality conditions
  -> apply BinarySignalEngine validation/risk/calibration gates
  -> produce CALL, PUT, or NO_SIGNAL
  -> optionally persist analytical signal in PostgreSQL
  -> return JSON response with audit metadata

Live market pipeline
--------------------

Provider REST/WebSocket/tick source
  -> normalize provider identity and source class
  -> validate OHLC/tick quality and timestamps
  -> store in CandleStore or TickBuffer
  -> construct closed candles when required
  -> compute features
  -> analyze market behavior and regime
  -> create AnalysisRequest
  -> route to relevant logical agents
  -> aggregate evidence
  -> apply validation, calibration, risk, and edge gates
  -> update live signal state
  -> publish dashboard/diagnostic information

500-agent design
---------------
The registry stores agent definitions and executable adapters, not 500 OS
processes. A request selects only matching agents. The orchestrator executes
them with bounded concurrency, normally MAX_AGENT_CONCURRENCY=10. Therefore,
creating 500 logical agents increases routing and execution work, but does not
start 500 processes for each request.

Effective decision chain
------------------------
There is no standalone class named MasterAgent. The master decision behavior is
distributed across:

- AgentRegistry: knows which agents exist and what they support.
- AgentOrchestrator: selects, schedules, retries, and aggregates agents.
- BinarySignalEngine: applies final directional-signal gates.
- LiveProviderBridge: connects live ticks to analysis and exposes master state.
- LiveSignalStateMachine: manages live signal lifecycle and expiry.

The dashboard calls this combined behavior the master agent.

src/migrate.ts
-------------
Migration entrypoint. Requires DATABASE_URL, reads SQL files from db/migrations,

src/worker.ts
-------------
Redis worker entrypoint. Requires REDIS_URL, claims jobs, and recognizes:
market-observation, backtest, monte-carlo, and stress-test. The current
handlers are placeholders and return immediately for supported types. Queue
infrastructure exists, but business processing is incomplete.

4. AGENT SYSTEM
============================================================

Agent data model
----------------
An agent definition contains:

- id
- role/type
- version
- lifecycle status
- capabilities
- supported timeframes
- supported regimes
- reliability
- executable function

Only ACTIVE and DEGRADED agents are eligible for routing. Agent execution
returns structured evidence including output direction, probability,
validation status, confidence metadata, provenance versions, latency, and
error state.

src/agents/registry.ts
----------------------
Owns registration and lookup. It stores executable metadata and functions,
not operating-system workers. It supports capability/timeframe/regime-based
relevance filtering and lifecycle states.

src/agents/types.ts
-------------------
Defines AnalysisRequest, AgentDefinition, AgentEvidence, OrchestrationResult,
agent status, directions, confidence metadata, audit records, and policy
contracts. These types are the contract between request handling, agents,
and final signal evaluation.

src/agents/catalog.ts
---------------------
Defines a broad capability inventory, including:

- ingestion and data quality
- feature extraction
- model families
- analysis strategies
- validation
- risk
- verification
- coordination/meta functions

createCapabilityAgent() creates UNDER_REVIEW placeholder agents. They return
NO_SIGNAL and UNVERIFIED rather than pretending to have a validated model.

src/agents/specialized.ts
-------------------------
Creates exactly 500 logical specialized agent definitions.

Four explicit agents include:
- trend-structure
- return-momentum
- candle-structure
- data-quality-gate

The remaining generated profiles cover trend, momentum, candle patterns,
volatility, range, regime, wick structure, multi-feature analysis, and
behavior. These are deterministic feature-rule adapters, not trained models.
Their evidence is UNVERIFIED, calibration is unknown, sample size is normally
zero, and uncertainty is high unless a real validated adapter replaces them.

Typical specialized-agent behavior:
- inspect featureValues and request regime
- emit CALL, PUT, or NO_SIGNAL
- explain the rule in evidence text
- mark unavailable features INVALID
- never claim out-of-sample validation without real evidence

src/agents/orchestrator.ts
--------------------------
This is the effective master coordinator for a single analysis request.

Responsibilities:
1. Filter agents by lifecycle status, capability, timeframe, and regime.
2. Enforce minimum-agent and selection policy.
3. Run selected agents through a bounded asynchronous pool.
4. Apply per-agent timeout.
5. Retry according to max retry policy.
6. Isolate failures so one agent does not crash the request.
7. Keep selected IDs, failures, attempt counts, and timestamps in audit data.
8. Aggregate direction votes and weighted probabilities.
9. Calculate agreement and evidence quality.
10. Return NO_SIGNAL when evidence is insufficient, conflicting, invalid, or
    outside policy.

Default policy values from the implementation/README are approximately:
- max concurrency: 10
- timeout: 1500 ms
- max retries: 1
- minimum agents: 3
- minimum agreement: 0.90
- minimum data quality: 85
- minimum probability edge: 0.02

The exact configured values can be overridden by environment/config.

Master-agent interpretation
---------------------------
The master agent is an architectural role, not a single file. Its control
loop is:

input market observation
  -> select applicable specialists
  -> run specialists safely
  -> aggregate their evidence
  -> reject unreliable evidence
  -> send aggregate result to final signal engine
  -> expose decision and reason to runtime/dashboard

This design avoids a monolithic model and makes every specialist auditable.
It also means that a displayed master decision is only as strong as the
provider quality, evidence quality, validation state, and final gates.

5. FINAL SIGNAL AND FAIL-CLOSED LOGIC
============================================================

src/signal-engine.ts
--------------------
BinarySignalEngine is the final policy boundary. It does not blindly trust
the orchestrator direction. It applies strict gates such as:

- data quality >= 85
- request validation status is VALIDATED
- out-of-sample validation is true
- walk-forward validation is true
- a horizon is selected
- no behavior contradiction
- regime is not UNKNOWN or ABNORMAL
- risk status is ACCEPTABLE
- representative evidence is valid
- representative sample size >= 100
- uncertainty is not HIGH
- calibration has not failed
- weighted probability clears minimum probability edge over break-even

For binary payout math, break-even probability is calculated from payout. For
an 80 percent payout, the break-even probability is about 0.555555. A model
probability below the configured edge requirement becomes NO_SIGNAL/WEAK_SIGNAL.

Successful output is still:
- signalType = ANALYTICAL_SIGNAL
- executionOrder = false

Failure states include data-quality warning, unknown regime, failed
calibration, restricted/blocked risk, weak signal, insufficient evidence,
contradiction, and other NO_SIGNAL reasons.

src/live-state.ts
-----------------
LiveSignalStateMachine tracks NO_DATA, waiting/analyzing, CALL/PUT, and STALE
states. It rejects already-expired signals and expires active signals when
validity ends.

src/probability-engine.ts
-------------------------
Provides probability calculations, calibration-related metrics, and
break-even/edge logic used by the signal and validation layers.

6. MARKET DATA AND PROVIDER ARCHITECTURE
============================================================

Provider contract
-----------------
src/market/provider.ts defines adapters for:

- instrument discovery
- supported timeframe discovery
- current candles
- historical candles
- candle subscriptions
- tick subscriptions
- health checks
- reconnect/disconnect

Every event carries provider identity, provider symbol, source class, source
timestamp, ingestion timestamp, quality status, and normalized market data.
This prevents a binary-options symbol from being silently represented as a
reference-market symbol.

ProviderRegistry
----------------
src/market/providers.ts registers seven provider identities:

1. Binance
2. OANDA
3. Finnhub
4. Quotex
5. Pocket Option
6. AlimTrade
7. Other binary-options providers

Reference-market adapters
-------------------------
BinanceSpotProvider
- official REST exchange metadata and kline adapter
- official candle WebSocket support
- reference-market source
- no native tick subscription in this adapter
- candles remain UNVERIFIED until quality/validation policy accepts them

OandaProvider
- requires account ID and API token
- official REST candles
- official pricing-stream ticks
- can build candles from ticks because native candle streaming is not exposed
- reference-market source

FinnhubProvider
- API-key-based REST candles
- WebSocket trade events
- tick-to-candle aggregation
- reference-market source

Binary-option adapters
----------------------
Quotex, Pocket Option, AlimTrade, and generic other-binary-options adapters
are deliberately not data substitutes. They generally provide no supported
instruments, candles, or ticks. Quotex reports NOT_VERIFIED/BLOCKED; the others
normally report NOT_SUPPORTED. They do not secretly use Binance data.

src/market/provider-priority.ts
--------------------------------
Chooses an available live source. Typical priority:

1. Deriv
2. Finnhub
3. Binance
4. OANDA

It can broadcast live ticks to subscribed consumers and maintains provider
identity when fallback occurs.

7. LIVE MARKET PIPELINES
============================================================

src/market/live-provider-bridge.ts
-----------------------------------
Connects provider events to analysis. For a live tick it generally:

1. normalizes provider data
2. detects a basic regime
3. updates/builds one-minute candles
4. records latency/tick/provider diagnostics
5. computes features
6. runs behavior analysis
7. applies algorithm/noise quality gates
8. creates AnalysisRequest
9. runs AgentOrchestrator
10. runs BinarySignalEngine
11. records master-agent decision and reason
12. publishes dashboard relay frames

Deriv bridge flow:
Deriv WebSocket -> normalized price event -> provider-priority
broadcast -> local one-minute CandleStore -> FeatureEngine -> behavior
engine -> quality gate -> orchestrator -> signal engine -> diagnostics.

src/market/live-pipeline.ts
---------------------------
LiveObservationPipeline connects provider discovery, InstrumentRegistry,
candle polling/subscriptions, CandleStore, EventStream, DataQualityEngine,
FeatureEngine, and live signal state. It is the candle-oriented pipeline.

src/market/live-tick-pipeline.ts
--------------------------------
LiveTickPipeline is the tick-oriented path. It supports:

- provider tick subscription
- rolling TickBuffer
- second-candle construction
- candle quality checks
- feature extraction
- behavior analysis
- orchestrator execution
- risk evaluation
- signal-state transitions

It demonstrates how 500 logical agents can be fanned out without 500
processes.

src/market/collection.ts
------------------------
Handles REST backfill, live subscriptions, reconnect attempts, normalization,
ordering, duplicates, and heartbeat monitoring.

src/market/observer.ts
----------------------
Discovers provider instruments, polls candles, and pushes observations into
the processing path.

src/market/candle-store.ts
--------------------------
Maintains current candles, versions, corrections, lifecycle state, and basic
candle validity. A corrected candle gets a new version rather than silently
overwriting history.

src/market/tick-buffer.ts
-------------------------
Stores ticks and buckets them into time windows/candles.

src/market/data-quality.ts
-------------------------
Checks duplicate data, gaps, OHLC relationships, freshness, outliers,
completeness, and quality scores. Low-quality data causes downstream
NO_SIGNAL rather than a fabricated directional result.

src/market/event-stream.ts
--------------------------
In-memory event/audit stream for market events and processing transitions.

src/market/instrument-registry.ts
---------------------------------
Tracks discovered instruments, provider availability, symbols, timeframes,
and source identity.

src/market/instrument-mapping.ts
--------------------------------
Keeps provider symbol identity separate. For example, a Quotex EUR/USD and a
Binance EURUSDT-like reference symbol remain different instrument identities
even when their labels look similar.

src/market/replay.ts
--------------------
Replays closed and validated candles into analysis/validation flows.

src/market/performance-memory.ts
--------------------------------
Keeps in-memory performance structures for agent/instrument/timeframe/regime
combinations.

8. FEATURES, BEHAVIOR, VALIDATION, RISK, AND SIMULATION
============================================================

src/feature-engine.ts
---------------------
Computes latest return, rolling return, range, candle body, body ratio,
upper/lower wick, short-window volatility, and momentum.

src/market/behavior-engine.ts
-----------------------------
Detects and evaluates:

- candle patterns
- same-direction sequences
- price-level reactions
- time-window behaviors
- volatility-regime transitions
- movement behavior
- pattern evolution

It also maintains pattern memory/context matching, agreement and contradiction
scores, uncertainty, validation state, horizon selection, and behavior gates.

src/market/historical-validation.ts
------------------------------------
Supports future-candle outcome labels, pending outcomes, hit rate,
precision/recall/F1, Brier score, log loss, calibration, drawdown, losing
streak, purged/embargoed splits, walk-forward validation, and pattern
validation lifecycle.

src/market/adaptive-horizon.ts
------------------------------
Supports 1, 5, 10, 15, 30, and 60 minute horizons. A usable horizon needs
at least 100 samples, out-of-sample performance, walk-forward stability,
compatible regime, non-high uncertainty, and accepted calibration.

src/validation-engine.ts
------------------------
Runs ordered historical backtests and walk-forward windows. It detects input
ordering/leakage problems and keeps validation explicitly historical.

src/monte-carlo-engine.ts
-------------------------
Runs seeded Monte Carlo simulations and returns reproducible ending-capital
percentiles. Results are simulation-only.

src/simulation-engine.ts
------------------------
Runs deterministic paper binary-options outcomes. It does not call a broker
and labels outputs simulationOnly.

src/risk-engine.ts
------------------
Evaluates capital usage, exposure, drawdown, losing streak, utilization, and
risk status. Restricted or blocked risk prevents a directional signal.

src/monitoring-engine.ts
------------------------
Provides distribution-drift and stress-test analysis.

src/model-registry.ts
---------------------
Defines model registration/version and activation eligibility. A model must
meet validation/calibration/metadata policy before activation. The current
server does not wire a full model-registry instance into /api/v1/models; that
endpoint reports unavailable/not available.

src/market/browser-observation.ts
----------------------------------
Implements an observation state machine:

open workspace
  -> user confirms login
  -> start observation
  -> discover submitted pairs
  -> accept submitted OHLC events
  -> data-quality checks
  -> features
  -> behavior
  -> orchestration
  -> final signal gate

The backend does not independently discover browser pairs. A caller must submit

src/quotex-ui-state.ts
----------------------
Normalizes provider UI state. Manual website login does not prove that a
permitted backend market-data interface exists. Quotex remains blocked unless
such an interface is explicitly verified.

tools/market-qx-observer
------------------------
The browser extension observes visible DOM fields only. It requires visible
pair, timeframe, and complete OHLC values. It refuses to synthesize candles
from price-only values, retries transport failures, and sends events to the
observation API.

It does not:
- inspect private WebSocket frames
- read cookies, credentials, or tokens
- read canvas pixels
- execute trades

Configuration issue: its default target is localhost:4000, while the
TypeScript server defaults to 3001 and Compose uses 6001. These values must be
aligned explicitly.

tools/ws-debugger and screen capture
-------------------------------------
Local-only WebSocket/debugging and screen-capture utilities. Screen outputs
are UNVERIFIED_SCREEN_CAPTURE and are not trusted provider candles.

14. REDIS JOB ARCHITECTURE
============================================================

src/jobs/queue.ts
-----------------
Redis job store uses ready sorted sets, dead-letter queue, idempotency keys,
due-job claiming, bounded attempts, and exponential retry delays.

Current limitation: complete() is effectively a no-op. Claimed jobs leave the
ready set, but completed-job durability/recording is not implemented.

src/worker.ts
-------------
The worker recognizes market-observation, backtest, monte-carlo, and
stress-test job types, but the current handlers are placeholders. Redis is a
foundation for asynchronous workloads, not a finished job-processing system.

17. IMPORTANT CURRENT GAPS AND RISKS
============================================================

1. Authentication is implemented but not wired to HTTP routes.
2. Redis job completion persistence is incomplete.
3. Worker job handlers are placeholders.
4. Many database tables are schema-ready but not fully connected to runtime
   repositories.
5. /api/v1/models does not expose a fully wired model registry.
6. Python SQLite and TypeScript PostgreSQL appear independent.
7. Port defaults differ across API, Compose, extension, and relays.
8. Both TypeScript and Python paths may try to own port 8080.
9. Browser observation depends on caller-submitted events; it is not an
   automatic authenticated provider feed.

    states. Current source should be treated as authoritative.
13. The live bridge can publish dashboard data without a complete demonstrated
    PostgreSQL persistence flow for every live candle.
14. The repository is analytical/simulation-only; no broker execution path is
    present.

18. END-TO-END EXPLANATION IN PLAIN LANGUAGE
============================================================

A market observation first enters through a provider adapter or an explicitly
submitted browser observation. The system preserves the source identity and
checks whether the data is complete, fresh, ordered, and mathematically valid.
It then computes technical features and behavior context.

The request is sent only to relevant logical agents. These agents are not
separate running applications. They are registered executable definitions,
limited by a worker pool so the system remains bounded even with 500 agents.
Each response must include evidence, probability/confidence metadata, version
information, and validation status.

The orchestrator combines the responses but does not have unlimited authority.
The final signal engine checks data quality, regime, validation, calibration,
horizon, uncertainty, agreement, risk, and payout-aware probability edge. Any
critical failure produces NO_SIGNAL. A successful result is an analytical
research signal and cannot be treated as a trading order.

The dashboard presents this state, while PostgreSQL is the primary structured
store for the TypeScript platform. Redis is intended for asynchronous jobs.
The Python relay is a separate local collection/display path using SQLite.
